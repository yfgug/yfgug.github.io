比赛复盘：做项目之外，我开始练习把东西讲清楚

发表于2026-06-13|更新于2026-06-13|比赛复盘
|总字数:1.1k|阅读时长:3分钟|浏览量:

起因

这段时间项目和比赛堆在一起，我最大的感受是：把东西做出来是一回事，把东西讲清楚是另一回事。

写代码的时候，我只需要关心功能能不能跑、逻辑通不通、页面能不能点。但一到比赛、申报、展示这种场景，问题就变了。

评委不一定会看你的每一行代码，也不一定有时间理解所有技术细节。你需要在很短的时间里说明白：

  • 你做了什么？
  • 为什么要做？
  • 解决了什么问题？
  • 你负责了哪部分？
  • 和普通 demo 比起来，有什么值得看的地方？

这件事比我想象中难。

项目不是功能清单

我以前写项目介绍，很容易写成这样：

系统实现了登录、注册、增删改查、文件上传、公告管理、订单结算、购物车、搜索、推荐……

这当然没错，但它不够好。

因为功能清单只能证明”我写了不少东西”，不能证明”这个项目为什么成立”。

后来我开始尝试换一种讲法：

先讲场景，再讲痛点，再讲方案，最后讲我怎么实现。

比如宿舍管理系统，不只是”学生管理 + 报修 + 公告”，而是：

宿舍日常管理里经常有信息维护、报修流转、通知发布这些重复工作，所以我用 Spring Boot 和 MyBatis 做了一个后台，把这些流程统一到一个系统里。

这样听起来就更像一个完整项目，而不是一堆按钮。

技术亮点要讲人话

比赛里讲技术，最怕变成背名词。

Spring Boot、MyBatis、RESTful API、动态 SQL、Session、连接池、AOP、事务，这些词当然能讲，但如果只堆名词，其实没有意义。

更好的方式是把技术点和问题绑在一起：

  • 多条件查询很容易写成一堆 if-else，所以用 MyBatis 动态 SQL。
  • 文件上传可能有安全风险，所以做后缀白名单、大小限制和 UUID 重命名。
  • 登录接口可能被暴力尝试，所以做失败次数记录和短时间锁定。
  • 购物车需要跨请求保存状态，所以用 Session 存当前订单。

这样讲，别人能知道你不是为了用技术而用技术，而是真的遇到了问题，然后用技术解决它。

展示材料也要像项目一样打磨

比赛准备里最容易被低估的是材料。

PPT、演示视频、项目 README、答辩稿，看起来都不是代码，但它们决定别人第一眼怎么理解你的项目。

我现在会给每个项目准备几样东西：

  • 一句话介绍：这个项目到底是什么。
  • 三个核心功能：别贪多，先讲最能代表项目的。
  • 一张流程图：说明用户怎么用、数据怎么走。
  • 一个技术架构图：说明前后端、数据库、关键模块。
  • 一段真实演示：从登录到完成核心流程。
  • 一页踩坑复盘：说明我真的做过，而不是只拼了页面。

这些材料准备好之后，不只是比赛能用，写博客、写简历、做项目展示也都能用。

我现在的整理方式

以后每个项目或者比赛结束，我打算按这个模板复盘：

  1. 背景：为什么做这个东西。
  2. 目标：它要解决什么问题。
  3. 我的工作：我负责了哪些模块。
  4. 技术实现：关键链路怎么跑通。
  5. 难点：哪里卡住过，怎么解决。
  6. 结果：完成到了什么程度。
  7. 反思：下次会怎么做得更好。

这个模板不花哨，但很管用。

因为它逼着我从”我做了很多”变成”我讲得清楚”。

最后

比赛最锻炼人的地方，不只是赶 ddl，也不是通宵改 bug。

它更像一次压缩训练：你要在有限时间里做选择、搭系统、写材料、做展示，还要面对别人直接问你”这个东西到底有什么用”。

被问住的时候挺尴尬，但也挺有价值。

因为那一刻你会发现，项目真正需要补的地方，不一定在代码里，也可能在表达里。

做出来，是第一步。

讲清楚，才算真的把它变成自己的东西。
